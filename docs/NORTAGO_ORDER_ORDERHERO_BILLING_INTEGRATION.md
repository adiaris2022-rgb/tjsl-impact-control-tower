# NORTAGO Order — OrderHero Billing Integration Specification

Status: implementation specification; credentials and live workspace configuration are not available in this repository session.
Decision date: 2026-11-17.

## 1. Approved commercial rules

- Billing unit: one outlet, not one business account.
- Monthly price: IDR 50,000 per outlet.
- Annual price: IDR 500,000 per outlet (IDR 100,000 / 16.7% lower than 12 monthly payments).
- Payment is manual/prepaid for each billing period. No automatic recurring charge is assumed.
- A business may own multiple outlets; every outlet has its own subscription, invoice, due date, and entitlement state.
- A payment for one outlet must never activate another outlet.

## 2. Correct division of OrderHero products

Do not conflate customer commerce checkout with subscription collection:

1. **Customer purchases inside NORTAGO Order:** use the merchant's published OrderHero Form Order URL per outlet (the selected product direction). NORTAGO sends the customer to the mapped Form Order page.
2. **NORTAGO subscription invoices:** use OrderHero **LinkBayar Payment Requests** to create an exact-amount bill for each internal subscription invoice. LinkBayar is the better fit because the invoice amount and reference_id are generated by NORTAGO and do not require a subscription product in the merchant catalogue.

The OrderHero API documentation lists LinkBayar POST /payment-requests, GET /payment-requests/{reference_id}, and payment_request.paid, .cancelled, and .expired webhooks. API availability is workspace/feature gated; an API key alone does not prove the workspace has LinkBayar enabled.

## 3. Subscription payment flow

1. An authenticated business Owner/Program Manager selects a business, outlet, and plan.
2. Server checks membership/role and confirms the outlet belongs to that business.
3. Server creates one internal invoice with a unique invoice_no, amount copied from the active plan (never from browser input), outlet/business/subscription IDs, and billing period.
4. Server calls OrderHero POST /payment-requests with:
   - reference_id: immutable internal invoice number;
   - amount: exact invoice amount in IDR;
   - title / description: NORTAGO outlet subscription and period;
   - return_url: NORTAGO invoice status page;
   - Idempotency-Key: stable key for that invoice creation attempt.
5. Store the returned provider reference and payment URL. Redirect the Owner to the OrderHero hosted payment page.
6. On payment_request.paid, verify HMAC-SHA256 over the raw body using the complete whsec_ secret, validate timestamp freshness, reject test events, and deduplicate by delivery_id.
7. Before changing money or entitlements, server re-reads GET /payment-requests/{reference_id} using the server-only API key. Confirm provider status is paid, reference matches the internal invoice, amount and currency match, and invoice has not already been settled.
8. In one database transaction, mark invoice PAID, payment VERIFIED, record the event, and activate/extend only the linked outlet subscription. A repeated webhook must be a no-op.
9. Handle payment_request.cancelled and payment_request.expired as invoice state updates only; they must not activate access.
10. Owner dashboard shows payment link, invoice status, active period, next due date, and renewal action. Reminders may be scheduled, but charging remains manual.

## 4. Period rules

- Monthly: period begins at confirmed activation/renewal timestamp and ends one calendar month later.
- Yearly: period begins at confirmed activation/renewal timestamp and ends one calendar year later.
- Use timezone-aware timestamps (store UTC; render Asia/Jakarta).
- Renewal paid before expiry extends from the existing period end; renewal paid after expiry starts from payment verification time. This prevents losing prepaid days.
- Grace period: keep as a product-policy setting, not an implicit provider behavior. Do not suspend outlets until the grace-period policy and customer notices are approved.
- Do not set auto_renew=true; no automatic recurring charge is implemented.

## 5. Required server configuration

- ORDERHERO_API_BASE_URL=https://api.orderhero.id/v1
- ORDERHERO_SECRET_KEY (server-only; least-privilege LinkBayar scopes)
- ORDERHERO_LINKBAYAR_WEBHOOK_SECRET (full whsec_ value)
- ORDERHERO_LINKBAYAR_ENABLED (explicit feature readiness flag)
- Existing Supabase service-role configuration, server-only.

Never expose secret keys in NEXT_PUBLIC_*, browser bundles, logs, error messages, or client-readable database rows. The API key must be created by the OrderHero workspace owner/admin. If the workspace returns FEATURE_NOT_AVAILABLE, stop and request feature enablement; do not silently fall back to an unverified payment method.

## 6. Security and reliability requirements

- Use server-side role checks for invoice creation; browser cannot choose amount, status, business_id, or subscription entitlement.
- Verify webhook signature against the raw request body before JSON parsing; use constant-time comparison and reject stale timestamps.
- Persist unique webhook delivery IDs; make processing idempotent.
- Treat webhook as notification, not source of truth. Re-read payment request before activating a subscription.
- Validate reference, amount, currency, and provider status against the internal invoice.
- Never trust return_url/browser redirect as proof of payment.
- Do not process the generic order_paid event as a second LinkBayar settlement when the dedicated payment_request.paid event is used.
- Queue noncritical work; return 2xx promptly after durable acceptance.
- Add rate limits and audit events for invoice creation and webhook processing.

## 7. Acceptance tests before enabling live collection

- Monthly invoice is exactly IDR 50,000; annual invoice is exactly IDR 500,000.
- Client-supplied amount tampering is ignored/rejected.
- Cross-business/outlet invoice creation is denied.
- Reusing an idempotency key does not create duplicate provider bills.
- Invalid HMAC, stale timestamp, test webhook, wrong reference, wrong amount, wrong currency, and unpaid provider status never activate access.
- Duplicate and out-of-order webhook deliveries are safe.
- A valid paid invoice activates only its own outlet and extends the correct period.
- Cancelled/expired invoices do not activate or extend access.
- API outage and unknown create outcome are reconciled by querying the same reference before retrying.
- CI runs migration and transactional smoke tests; Supabase staging tests real Auth/RLS/tenant roles before production.

No live API key, webhook secret, published Form Order URL mapping, or enabled LinkBayar workspace was available in this repository session. ## 10. Implemented application layer (2026-11-17)

The feature branch now contains (CI workflow updated to validate the new billing migration):
- `app/otc/subscribe`: authenticated owner/Program Manager subscription page; loads business memberships and active outlets, lets the user select multiple outlets, and displays the aggregate amount.
- `POST /api/nortago/subscriptions/checkout`: validates the user's Supabase bearer session, calls the authenticated invoice RPC once per selected outlet, then creates one OrderHero LinkBayar payment request per invoice using its server-generated invoice number as both `reference_id` and `Idempotency-Key`.
- `POST /api/nortago/subscriptions/webhook`: validates the LinkBayar HMAC-SHA256 signature over timestamp + raw body, rejects stale signatures and test events, re-reads the provider payment request, and calls a restricted server-only settlement RPC.
- `20261117_nortago_order_subscription_billing_v1.sql`: creates authenticated invoice preparation and server-only settlement functions, plus a webhook delivery deduplication ledger.
- `nortago_subscription_billing_smoke.sql`: asserts function presence, grants, and delivery-ledger RLS.
- CI applies the billing migration and runs its security smoke checks.

The UI creates a separate invoice per outlet. The displayed aggregate is informational; it does not create a single combined bill. A partial multi-outlet result is returned explicitly so a failed outlet does not silently appear paid.

## 11. Required deployment configuration and OrderHero workspace setup

Server-side environment variables:
- `ORDERHERO_SECRET_KEY`: secret API key created by the OrderHero workspace owner, with LinkBayar payment-request read/write scopes.
- `ORDERHERO_LINKBAYAR_ENABLED=true`: explicit operator feature flag; keep false until access is confirmed.
- `ORDERHERO_LINKBAYAR_WEBHOOK_SECRET`: full webhook secret including `whsec_`.
- `SUPABASE_SERVICE_ROLE_KEY`: server-only service role key; never prefix with `NEXT_PUBLIC_`.
- `NEXT_PUBLIC_APP_URL`: canonical public HTTPS application origin used for payment return URL.

In the OrderHero workspace:
1. Obtain LinkBayar programme access; the feature may return `FEATURE_NOT_AVAILABLE / NOT_WHITELISTED` otherwise.
2. Enable Plugin → LinkBayar and ensure ePayment plus at least one payment channel are active.
3. Create a secret API key as workspace owner with `payment_requests:read` and `payment_requests:write`.
4. Configure LinkBayar paid notifications to `https://<app-host>/api/nortago/subscriptions/webhook`.
5. Copy the full webhook secret into the server environment.

Do not enable the feature flag or deploy live collection until staging has verified a successful payment, a duplicate webhook, a bad signature, a wrong amount, and an expired/cancelled bill. The webhook endpoint re-reads the bill from OrderHero before settlement; the browser return URL never activates access.

## 12. Operational caveats

- One invoice and one payment link are created per selected outlet. Customers must complete each outlet payment separately.
- The current endpoint reuses an existing open invoice on a retry and reports partial failures explicitly. Operators should reconcile open invoices before asking customers to retry.
- The authenticated invoice RPC relies on the existing `has_business_role(business_id, ['OWNER','PROGRAM_MANAGER'])` policy contract.
- No live secrets, workspace access, Supabase staging credentials, or production deployment are available in this repository session. These changes are code and migration artifacts only.
